# Condo Management (frontend)

โครงหน้าบ้านของระบบบริหารคอนโด/นิติบุคคล: React + Vite + TypeScript + Tailwind v4

สถานะ: โครงพื้นฐาน + **login/สมัครสมาชิก/สิทธิ์ตาม role** + **ห้องชุด/สัญญาเช่า/ตรวจสภาพห้อง** (FR3–10) + **มิเตอร์/ใบแจ้งหนี้/การชำระเงิน/ใบเสร็จ/แจ้งเตือน** (FR11–17) + **แจ้งซ่อมและงานช่าง** (FR18–21) + **จองส่วนกลางและพัสดุ** (FR22–25) ทั้งหมดเป็นข้อมูลจำลองในเบราว์เซอร์ ยังไม่มีหลังบ้านจริง หน้าของโมดูลอื่นที่เหลือเป็น placeholder

## คำสั่ง

```bash
npm install
npm run dev     # เปิดเซิร์ฟเวอร์พัฒนา
npm test        # vitest (jsdom)
npm run build   # tsc + vite build
npm run lint    # oxlint
```

```

  property/    ห้อง/สัญญา/ตรวจสภาพ: types, rules (กฎล้วน), seed, localPropertyApi, PropertyProvider/useProperty
  maintenance/ แจ้งซ่อม/งานช่าง: types, rules (กฎล้วน), seed, photos (ย่อรูป), localMaintenanceApi, MaintenanceProvider/useMaintenance
  facilities/  จองส่วนกลาง/พัสดุ: types, rules (กฎล้วน), seed, localFacilitiesApi, FacilitiesProvider/useFacilities
  notifications/ useNotifications: รวมแจ้งเตือนบิล งานซ่อม การจอง และพัสดุของกระดิ่ง
  billing/     มิเตอร์/ใบแจ้งหนี้/สลิป/ใบเสร็จ/แจ้งเตือน: types, periods, rules (กฎล้วน), seed, localBillingApi, BillingProvider/useBilling
  features/    หน้าของแต่ละโมดูล (auth/ = login+สมัคร, units/ = ห้อง/สัญญา/ตรวจสภาพ, billing/ = บิลของผู้เช่าและของนิติบุคคล, maintenance/ = แจ้งซ่อม งานนิติบุคคลและงานช่าง, facilities/ = จองส่วนกลางและพัสดุ, PlaceholderPage, NotFoundPage)
  components/  Button, StatusBadge, KpiCard, FormField, DataTable, Modal, ConfirmDialog, Pager, LanguageToggle
  i18n/        config + th.json / en.json
  styles/      index.css (Tailwind + design tokens ใน @theme)
```

- Design tokens มาจาก `DESIGN.md` ของ Juristic Core และอยู่ที่ `src/styles/index.css` ที่เดียว
- ฟอนต์ self-host ด้วย `@fontsource` (Plus Jakarta Sans, Noto Sans Thai, Material Symbols) ไม่พึ่ง CDN
- ตัวเลขเงิน/รหัสห้อง/มิเตอร์ใช้คลาส `tabular-nums`

## เพิ่มหน้าหรือเมนูใหม่ของ role

1. เพิ่มรายการใน `NAV_BY_ROLE` ที่ `src/app/roles.ts` (`key`, `path` ขึ้นต้นด้วย `/<role>/`, `icon`)
2. เพิ่มป้ายชื่อ `nav.<key>` ใน `src/i18n/th.json` และ `en.json` (เทสจะ fail ถ้าขาดภาษาใดภาษาหนึ่ง)
3. เปลี่ยน element ของ route นั้นใน `src/app/router.tsx` จาก `PlaceholderPage` เป็นหน้าจริง

## ข้อความ (i18n)

ห้ามฝังข้อความ UI ในโค้ด ใช้ `useTranslation()` และ `t('กลุ่ม.คีย์')` ภาษาเริ่มต้นคือไทย ค่าที่ผู้ใช้เลือกเก็บใน localStorage คีย์ `condo:lang`

## ระบบ login (แบบจำลอง)

ไม่มีหลังบ้าน ข้อมูลทั้งหมดอยู่ใน localStorage ของเบราว์เซอร์ (`condo:users`, `condo:session`)

- **บัญชีทดลอง** (รหัสผ่านทุกบัญชี `demo1234`): `tenant01` ผู้เช่า, `staff01` นิติบุคคล, `tech01` ช่าง หน้า login มีปุ่มกรอกให้
- **สมัครสมาชิก** ได้เฉพาะผู้เช่า (`/register`) ตาม FR1; บัญชีนิติบุคคลและช่างมีแค่บัญชีทดลอง
- **สิทธิ์:** ยังไม่ล็อกอินจะถูกพาไป `/login`; เข้า URL ของ role อื่นจะถูกพากลับหน้าแรกของ role ตัวเอง
- รหัสผ่านเก็บเป็น hash SHA-256 ไม่เก็บ plain text แต่ localStorage แก้ได้เองในเบราว์เซอร์
- **ตัวจำลองนี้ไม่ปลอดภัยจริงและไม่ตรง NFR1 (PDPA/การเข้ารหัส)** ใช้เพื่อพัฒนาหน้าจอเท่านั้น

### เปลี่ยนเป็นหลังบ้านจริง

หน้าจอทั้งหมดเรียกผ่าน `useAuth()` ซึ่งอ่านจาก `AuthApi` (`src/auth/types.ts`: `register`, `login`, `logout`, `currentUser`) ถ้ามีหลังบ้านให้เขียน `AuthApi` ตัวใหม่ที่เรียก HTTP แล้วส่งให้ `<AuthProvider api={...}>` ที่ `src/App.tsx` แล้วลบ `localAuthApi.ts`, `demoAccounts.ts` และแผง "บัญชีทดลอง" ใน `LoginPage.tsx`

### ในเทส

`renderApp(path, { as: 'tenant' })` จาก `src/test/renderApp.tsx` เรนเดอร์ทั้งแอปที่ path นั้นโดยล็อกอินเป็น role ที่ระบุไว้แล้ว (หรือไม่ล็อกอินถ้าไม่ส่ง `as`)

## ห้องชุด สัญญาเช่า และตรวจสภาพห้อง (FR3–10)

หน้า `/juristic/units` (เฉพาะนิติบุคคล) มี 3 แท็บ: ห้องชุด, สัญญาเช่า, ตรวจสภาพ (`/leases`, `/inspections`)

- **ข้อมูล** อยู่ใน localStorage คีย์เดียว `condo:property` ถ้าว่าง/เสีย/อ้างอิงไม่ตรงกัน จะ seed ข้อมูลตัวอย่างใหม่ (ห้อง 24, สัญญา 9, บันทึกตรวจ 6) จาก `src/property/seed.ts` โดยวันที่ทั้งหมดอิงจาก "วันนี้"
- **สถานะห้องและสัญญา คำนวณ ไม่เก็บ** (`src/property/rules.ts`): ห้อง = ปิดปรับปรุง > มีผู้เช่า > เจ้าของอยู่เอง > ว่าง; สัญญา = ยกเลิก > หมดอายุ > ยังไม่เริ่ม > ใช้งาน และใช้งานที่เหลือ ≤ 60 วันได้ป้าย "ใกล้หมดอายุ"
- **กฎสำคัญ:** รหัสห้องไม่ซ้ำ; ลบห้องที่มีสัญญาไม่ได้ (ให้ปิดปรับปรุง); ช่วงสัญญาของห้องเดียวกันห้ามซ้อน (วันสิ้นสุดตรงกับวันเริ่มของอีกสัญญาก็ซ้อน); สัญญาที่ยกเลิก/หมดอายุแก้ไขไม่ได้; ต่อสัญญามีตรวจเข้า/ตรวจออกอย่างละ 1 ครั้ง แก้ได้แต่ลบไม่ได้
- **ชั้นข้อมูล:** หน้าจอเรียกผ่าน `useProperty()` ซึ่งอ่านจาก `PropertyApi` (`src/property/types.ts`) ถ้ามีหลังบ้านให้เขียน `PropertyApi` ตัวใหม่ แล้วส่งให้ `<PropertyProvider api={...}>` (ใน `UnitsPage`) และลบ `localPropertyApi.ts` กับ `seed.ts`
- **ในเทส:** `renderProperty(<UnitsTab />)` และ `makeTestApi()` จาก `src/test/renderProperty.tsx` ให้ข้อมูลตัวอย่างสดใหม่ทุกเทสโดยวันนี้คงที่ `2026-11-08`; เทสที่แก้ข้อมูลต้องใช้ตัวนี้ ไม่ใช้ `renderApp` (ตัวหลังใช้ api ตัวเดียวร่วมกันทั้งไฟล์)
- **ยังไม่ทำ:** ผังชั้น, ประวัติโอนกรรมสิทธิ์, หุ้นเจ้าของร่วม, escrow มัดจำ, พิมพ์/ส่งออกสัญญา, รูปถ่ายประกอบการตรวจ

## มิเตอร์ ใบแจ้งหนี้ และการชำระเงิน (FR11–17)

ไฟล์: `src/billing/` (ข้อมูลและกฎ), `src/features/billing/` (หน้าจอ), `src/app/NotificationBell.tsx` (กระดิ่งของผู้เช่า)

- **นิติบุคคล** `/juristic/billing` มี 4 แท็บ: จดมิเตอร์ (เลือกรอบเดือนได้ ค่าจำรอบไว้ใน `?period=YYYY-MM`), ใบแจ้งหนี้ (กรองสถานะ, ออกใบเสร็จ), สลิปชำระเงิน (คิวอนุมัติ/ปฏิเสธพร้อมเหตุผล), อัตราค่าบริการ
- **ผู้เช่า** `/tenant/billing` เห็นเฉพาะใบแจ้งหนี้ที่ออกให้ **เบอร์โทรเดียวกับบัญชี** (ไม่ใช่ตามชื่อ) เบอร์ของ `tenant01` คือ `0810000001` ผู้เช่าที่สมัครเองด้วยเบอร์ที่ไม่ตรงกับสัญญาใดจะเห็น "ยังไม่มีใบแจ้งหนี้" ผู้เช่าเปิดบิลดู QR ตัวอย่าง (ไม่ใช่ QR จริง) แนบสลิป `.jpg/.png` ไม่เกิน 5 MB แล้วดูใบเสร็จ
- **กฎคำนวณ** (`src/billing/rules.ts`): ค่าน้ำ = หน่วย × อัตรา, ค่าไฟ = หน่วย × อัตรา, ค่าส่วนกลาง = ตร.ม. × อัตรา; ปัดแต่ละบรรทัดเป็นบาทเต็ม (ครึ่งปัดขึ้น) แล้วค่อยรวม จึงยอดรวมเท่ากับผลบวกของบรรทัดบนใบแจ้งหนี้เสมอ; ครบกำหนดวันที่ 5 ของเดือนถัดไป; เลขก่อนหน้าต้องเท่ากับเลขปัจจุบันของรอบก่อน; แก้เลขมิเตอร์ของรอบเก่าได้ตราบที่รอบนั้นและรอบถัดไปของห้องยังไม่ออกบิล (เลขก่อนหน้าของรอบถัดไปจะปรับตามให้ และเลขปัจจุบันใหม่ต้องไม่เกินเลขของรอบถัดไป); ห้องที่ปิดปรับปรุงไม่ถูกเรียกเก็บแม้มีสัญญา
- **สถานะคำนวณ ไม่เก็บ:** ชำระแล้ว (มีสลิปอนุมัติ) > รอตรวจสลิป > เกินกำหนด > ยังไม่ชำระ; "รอออกใบเสร็จ" คือชำระแล้วแต่ยังไม่มีใบเสร็จ
- **แจ้งเตือนในแอปแทน push:** ออกใบแจ้งหนี้ / สลิปถูกปฏิเสธ / ออกใบเสร็จ ขึ้นที่กระดิ่งของผู้เช่า (ตามเบอร์โทร) กดแล้วไปที่ `/tenant/billing?invoice=<id>`
- **ข้อมูล** อยู่ใน `condo:billing` คีย์เดียว ถ้าว่าง/เสีย/ไม่สอดคล้องกับ `condo:property` จะ seed ข้อมูลตัวอย่างใหม่ (ย้อนหลัง 3 เดือน + เดือนปัจจุบันที่ยังจดไม่ครบ) โดยอิงจาก "วันนี้"
- **ข้อจำกัด:** สลิปเก็บแค่ชื่อไฟล์/ขนาด/ชนิด ไม่เก็บรูป; ไม่มีการแก้ไขหรือยกเลิกใบแจ้งหนี้หลังออกแล้ว; QR และใบเสร็จเป็นตัวอย่าง ไม่ใช่เอกสารทางภาษี; **บัญชีเดิมใน `condo:users` (ก่อนมีฟิลด์เบอร์โทรของบัญชีทดลอง) ต้องล้าง** (ลบคีย์ `condo:users` ใน DevTools แล้วรีเฟรช) ไม่เช่นนั้น `tenant01` จะไม่มีเบอร์ตรงกับบิล
- **เปลี่ยนเป็นหลังบ้านจริง:** หน้าจอเรียกผ่าน `useBilling()` ซึ่งอ่านจาก `BillingApi` (`src/billing/types.ts`) ให้เขียน `BillingApi` ตัวใหม่ที่เรียก HTTP แล้วส่งให้ `<BillingProvider api={...}>` (ใน `AppShell`) และลบ `localBillingApi.ts` กับ `seed.ts`
- **ในเทส:** `renderBilling(<Tab />, { as, api, property })` และ `makeTestBilling()` จาก `src/test/` ให้ข้อมูลสดใหม่ทุกเทสโดยวันนี้คงที่ `2026-11-08`; หน้าที่ต้องผ่านเราเตอร์จริงใช้ `renderApp` (localStorage ถูกล้างหลังทุกเทส)
- **ยังไม่ทำ:** ส่งอีเมล/SMS/push จริง, ยกเลิก/แก้ใบแจ้งหนี้, ค่าปรับล่าช้า, รายงานรายได้, พิมพ์ใบแจ้งหนี้/ใบเสร็จเป็น PDF

## แจ้งซ่อมและงานช่าง (FR18–21)

ไฟล์: `src/maintenance/` (ข้อมูลและกฎ), `src/features/maintenance/` (หน้าจอ), `src/notifications/` + `src/app/NotificationBell.tsx` (กระดิ่งรวม)

- **ผู้เช่า** `/tenant/maintenance`: แจ้งซ่อมใหม่ (หมวดหมู่, หัวข้อ, รายละเอียด, รูป 1–3 รูป — ไม่แนบรูปบันทึกไม่ได้) รหัส `MR-0001`… ดูรายการของตนพร้อมรูปและเส้นเวลาสถานะ **นิติบุคคล** `/juristic/maintenance`: ตารางทุกรายการ กรองสถานะ มอบหมาย/เปลี่ยนช่าง **ช่าง** `/technician/jobs`: เห็นเฉพาะงานที่ได้รับ อัปเดตทีละขั้น พร้อมหมายเหตุ
- **สถานะ (เก็บ ไม่คำนวณ):** รอการมอบหมาย → มอบหมายแล้ว → กำลังซ่อม → เสร็จสิ้น ไปหน้าอย่างเดียว ไม่ข้ามขั้น ไม่ย้อน; เปลี่ยนช่างได้จนกว่าช่างจะเริ่มงาน (ตอนเปลี่ยนช่าง แจ้งเฉพาะช่างคนใหม่) ทุกขั้นเก็บประวัติ (วันที่ หมายเหตุ ผู้ทำ)
- **ห้องของผู้เช่า** หาจากเบอร์โทรของบัญชี → สัญญาเช่าที่ใช้งานอยู่วันนี้ ไม่มีสัญญาจะแจ้งซ่อมไม่ได้ (มีข้อความอธิบาย) **ช่างจับคู่กับบัญชีด้วยเบอร์โทร:** `tech01` = `0800000002` (ช่างอีก 2 คนเป็นรายชื่อตัวอย่างสำหรับเลือกมอบหมาย ล็อกอินไม่ได้)
- **รูปภาพ:** ย่อเป็น JPEG ด้านยาวสุด 300px (คุณภาพ 0.7) ในเบราว์เซอร์แล้วเก็บเป็น data URL ใน `condo:maintenance` (ประมาณ 5–10 KB ต่อรูป); ไฟล์ต้นฉบับ `.jpg/.png/.webp` ไม่เกิน 10 MB **ถ้า localStorage เต็ม** จะไม่สร้างรายการ และแจ้งผู้ใช้ให้ลดจำนวนรูปหรือลบข้อมูลเก่า (ไม่เก็บไว้ในหน่วยความจำเงียบ ๆ)
- **กระดิ่งแจ้งเตือนรวมทุกบทบาท:** ผู้เช่าได้ทั้งแจ้งเตือนบิลและงานซ่อม (ตามเบอร์โทร) นิติบุคคลได้แจ้งซ่อมใหม่ ช่างได้งานที่ถูกมอบหมาย กดแล้วไปที่รายการนั้น (`?request=<id>`) และทำเครื่องหมายอ่านแล้ว
- **ข้อมูล** อยู่ใน `condo:maintenance` คีย์เดียว ถ้าว่าง/เสีย/รูปผิด จะ seed ข้อมูลตัวอย่างใหม่ (7 รายการ ครบทุกสถานะ) **แก้ห้อง/สัญญาแล้วงานซ่อมไม่หาย** (ล้างเฉพาะเมื่อไม่มีห้องที่อ้างถึงเหลือเลย) เพราะรายการเก็บ snapshot ของห้องและผู้เช่าไว้
- **ข้อจำกัด:** ไม่มีแก้ไข/ยกเลิกรายการ, ไม่มีนัดเวลา ค่าใช้จ่าย ให้คะแนน แชท, ไม่มี push จริง, สิทธิ์ตรวจฝั่งไคลเอนต์เท่านั้น, รูปไม่ผ่านการตรวจเนื้อหา, ไฟล์ที่เบราว์เซอร์ถอดรหัสไม่ได้ (เช่น HEIC บางรุ่น) จะถูกปฏิเสธ; **ต้องล้างคีย์ `condo:users` เดิม** เพื่อให้ `tech01` ได้เบอร์ใหม่ (ไม่เช่นนั้นจะไม่เห็นงาน)
- **เปลี่ยนเป็นหลังบ้านจริง:** เขียน `MaintenanceApi` (`src/maintenance/types.ts`) ตัวใหม่แล้วส่งให้ `<MaintenanceProvider api={...}>` (ใน `AppShell`) และลบ `localMaintenanceApi.ts` กับ `seed.ts`; การย่อรูป (`photos.ts`) ย้ายไปทำฝั่งเซิร์ฟเวอร์ได้
- **ในเทส:** `renderMaintenance(<Page />, { as, api, property })` และ `makeTestMaintenance()` จาก `src/test/` ให้ข้อมูลสดใหม่ทุกเทสโดยวันนี้คงที่ `2026-11-08`; ฟอร์มรับ `processor` ปลอมแทนการย่อรูปจริง (`fakePhoto`)
- **ยังไม่ทำ:** ลำดับความสำคัญ/SLA, แนบวิดีโอ, ส่งอีเมล/SMS แจ้งช่าง

## จองส่วนกลางและพัสดุ (FR22–25)

ไฟล์: `src/facilities/` (ข้อมูลและกฎ), `src/features/facilities/` (หน้าจอ), `src/notifications/` + `src/app/NotificationBell.tsx` (กระดิ่งรวม)

- **ผู้เช่า** `/tenant/facilities`: การ์ดส่วนกลาง 4 แห่ง (สระว่ายน้ำ 20 คน, ฟิตเนส 15, ห้องประชุม 10, ลานบาร์บีคิว 12 — ข้อมูลตั้งต้น ลานบาร์บีคิวปิดปรับปรุงเพื่อให้เห็นสถานะ) แถบที่ว่างรายชั่วโมงของวันที่เลือก (เป็นตัวเลขและข้อความ ไม่พึ่งสีอย่างเดียว) โควตาที่เหลือ ฟอร์มจอง ประวัติการจอง ยกเลิกได้ `/tenant/parcels` ("พัสดุของฉัน"): พัสดุรอรับและรับแล้วของห้องตน **นิติบุคคล** `/juristic/parcels-bookings` สองแท็บ: *การจอง* (ยืนยัน/ปฏิเสธพร้อมเหตุผล, ปิด-เปิดส่วนกลางชั่วคราว) และ *พัสดุ* (`/parcels`: ลงทะเบียนพัสดุรับเข้า, ทำเครื่องหมายรับแล้ว)
- **กฎการจอง** (`src/facilities/rules.ts`): จองล่วงหน้าตั้งแต่พรุ่งนี้ถึง 14 วัน (ไม่จองวันนี้เพราะระบบไม่รู้เวลาปัจจุบันอย่างน่าเชื่อถือ), ครั้งละ 1–3 ชั่วโมงเต็มภายในเวลาเปิด, ผู้ใช้ 1–5 คน (รวมผู้จอง), **ความจุรายชั่วโมง:** ทุกชั่วโมงในช่วงที่ขอ ผู้ใช้รวมของการจองที่ "รอยืนยัน" และ "ยืนยันแล้ว" บวกที่ขอต้องไม่เกินความจุ (เต็มพอดีผ่าน เกิน 1 คนไม่ผ่าน), **โควตา:** ห้องละไม่เกิน 2 การจอง (รอยืนยัน+ยืนยันแล้ว) ต่อสัปดาห์ จันทร์–อาทิตย์ นับตามวันที่ใช้บริการ ยกเลิกหรือถูกปฏิเสธแล้วคืนโควตา, ส่วนกลางที่ปิดจองไม่ได้ (การจองเดิมไม่ถูกยกเลิกอัตโนมัติ)
- **สถานะการจอง (เก็บ ไม่คำนวณ):** รอยืนยันการจองส่วนกลาง → ยืนยันแล้ว | ปฏิเสธ (ต้องมีเหตุผล); ผู้เช่ายกเลิกได้จนถึงก่อนวันใช้บริการ นิติบุคคลตัดสินได้จนถึงวันใช้บริการ; ทุกขั้นเก็บประวัติ **พัสดุ:** รอรับ → รับแล้ว ลงทะเบียนได้เฉพาะห้องที่มีสัญญาเช่าใช้งานอยู่ ผู้รับคือผู้เช่าของสัญญานั้น ไม่มีแก้ไข/ลบ
- **ห้องของผู้เช่า** หาจากเบอร์โทรของบัญชี → สัญญาเช่าที่ใช้งานอยู่วันนี้ ไม่มี → จองไม่ได้ (มีข้อความอธิบาย)
- **แจ้งเตือนในกระดิ่งรวม** (บิล + งานซ่อม + การจอง/พัสดุ): จองใหม่และผู้เช่ายกเลิก → นิติบุคคล; ยืนยัน/ปฏิเสธและพัสดุมาถึง → ผู้เช่า; **กรองชนิดแจ้งเตือนตามบทบาท** (เบอร์โทรเหมือนกันแต่คนละบทบาทจะไม่เห็นของอีกบทบาท)
- **ข้อมูล** อยู่ใน `condo:facilities` คีย์เดียว ถ้าว่าง/เสีย/ผิดกฎ (เช่น ความจุเกิน โควตาเกิน ประวัติกระโดดขั้น) จะ seed ข้อมูลตัวอย่างใหม่ **แก้ห้อง/สัญญาแล้วการจองและพัสดุไม่หาย** (ล้างเฉพาะเมื่อไม่มีห้องที่อ้างถึงเหลือเลย) **ทุกการเขียนที่คนพึ่งพา** (จอง, ตัดสิน, ยกเลิก, ปิด-เปิด, ลงทะเบียนพัสดุ) ทำแบบเคร่งครัด: ถ้า localStorage เต็มจะขึ้นข้อความและไม่เปลี่ยนอะไร
- **ข้อจำกัด:** ไม่มี QR เข้าประตู/ตู้ล็อกเกอร์จริง ("ที่วาง" เป็นแค่ป้ายบอก), ไม่มีหน้าตั้งค่าส่วนกลาง/โควตา, นิติบุคคลจองแทนลูกบ้านไม่ได้, ไม่แก้/ลบพัสดุหลังลงทะเบียน, ไม่มีแจ้งเตือนพัสดุค้างซ้ำ, ความจุและโควตาตรวจฝั่งไคลเอนต์ในเบราว์เซอร์เดียว (หลายเครื่องจริงต้องให้หลังบ้านตัดสิน), เบอร์โทรเป็นตัวตนเดียวที่เชื่อมบัญชีกับสัญญา, ไม่มี push จริง
- **เปลี่ยนเป็นหลังบ้านจริง:** เขียน `FacilitiesApi` (`src/facilities/types.ts`) ตัวใหม่แล้วส่งให้ `<FacilitiesProvider api={...}>` (ใน `AppShell`) และลบ `localFacilitiesApi.ts` กับ `seed.ts`; กฎใน `rules.ts` ย้ายไปบังคับฝั่งเซิร์ฟเวอร์ได้
- **ในเทส:** `renderFacilities(<Page />, { as, api, property })` และ `makeTestFacilities()` จาก `src/test/` ให้ข้อมูลสดใหม่ทุกเทสโดยวันนี้คงที่ `2026-11-08` (ข้อมูลตัวอย่างของห้อง A-1204 ใช้โควตาสัปดาห์ของวันถัดไปไว้แล้ว เทสที่จองใหม่ให้ใช้วันที่ห่างออกไป เช่น +12 วัน)
- **ยังไม่ทำ:** จองแทนลูกบ้าน, ค่าบริการ/มัดจำ, พิมพ์รายงานการใช้งาน, แจ้งเตือนซ้ำเมื่อพัสดุค้าง
