# Maintenance Requests & Technician Jobs — Design Spec

วันที่: 2026-11-09
Requirement: PDF ITDS262 — FR18 (ผู้เช่าแจ้งซ่อมพร้อมแนบรูปภาพ), FR19 (นิติบุคคลมอบหมายงานให้ช่างประจำโครงการ), FR20 (ช่างอัปเดตสถานะการซ่อม), FR21 (ผู้เช่าติดตามสถานะ); use case "สร้างรายการแจ้งการซ่อมแซม": ไม่กรอกครบ/ไม่แนบรูปต้องบันทึกไม่ได้และแจ้ง error, สถานะเริ่มต้น "รอการมอบหมาย", แจ้งเตือนไปยังนิติบุคคล
ต่อจาก: `2026-11-08-billing-design.md` (รูปแบบเดียวกัน: กฎล้วน → api จำลองใน localStorage → Provider → หน้าจอ)

## 1. เป้าหมาย

ผู้เช่าแจ้งซ่อมพร้อมรูปและติดตามสถานะได้ นิติบุคคลเห็นทุกรายการและมอบหมายช่าง ช่างเห็นเฉพาะงานของตนและอัปเดตสถานะได้ ทั้งหมดเป็นข้อมูลจำลองในเบราว์เซอร์ (ไม่มีหลังบ้าน) และสลับเป็นหลังบ้านจริงได้โดยเขียน `MaintenanceApi` ตัวใหม่

## 2. ขอบเขต

- **ผู้เช่า** `/tenant/maintenance`: รายการแจ้งซ่อมของตน (การ์ด + ป้ายสถานะ), ปุ่ม "แจ้งซ่อมใหม่" (หมวดหมู่, หัวข้อ, รายละเอียด, รูป 1–3 รูป), รายละเอียดพร้อมรูปและเส้นเวลาสถานะ (FR18, FR21)
- **นิติบุคคล** `/juristic/maintenance`: ตารางทุกรายการ กรองสถานะ, ดูรายละเอียด/รูป/เส้นเวลา, มอบหมายและเปลี่ยนช่างขณะยังไม่เริ่มงาน (FR19)
- **ช่าง** `/technician/jobs`: เฉพาะงานที่มอบหมายให้ตน, อัปเดตสถานะพร้อมหมายเหตุ (FR20)
- **กระดิ่งแจ้งเตือนรวมทุกบทบาท** แสดงแจ้งเตือนบิล (เฉพาะผู้เช่า เหมือนเดิม) และแจ้งเตือนงานซ่อมของแต่ละบทบาท

**ไม่ทำรอบนี้:** แก้ไข/ยกเลิกรายการ, นัดเวลาเข้าซ่อม, ค่าใช้จ่ายและใบเสนอราคา, ให้คะแนนช่าง, แชท, ลำดับความสำคัญ/SLA, push จริง (NFR5), บัญชีช่างเพิ่ม (มีแค่ `tech01`; ช่างคนอื่นเป็นรายชื่อตัวอย่างสำหรับเลือกมอบหมาย)

## 3. การตัดสินใจ

| เรื่อง | ตัดสินใจ |
|---|---|
| รูปภาพ | ย่อเป็น JPEG ด้านยาวสุด 300px คุณภาพ 0.7 แล้วเก็บเป็น data URL ใน `condo:maintenance`; 1–3 รูปต่อรายการ; รับ `.jpg/.jpeg/.png/.webp` ต้นฉบับไม่เกิน 10 MB; การย่อรูปเป็นฟังก์ชันที่ฉีดเข้าไปได้ (เทสใน jsdom ใช้ตัวปลอม) |
| พื้นที่เก็บเต็ม | ถ้าเขียน localStorage ไม่สำเร็จตอนสร้างรายการ api จะล้มด้วย `storage_failed` และไม่สร้างรายการ (ไม่ใช้ memory fallback เงียบ ๆ แบบบิล เพราะรูปทำให้เต็มได้จริง) ผู้ใช้เห็นข้อความให้ลบรูปหรือลดจำนวน |
| ห้องของผู้เช่า | หาจากเบอร์โทรของบัญชี → สัญญาที่ใช้งานอยู่วันนี้ (ใช้ข้อมูล `condo:property`); ไม่มีสัญญา → แจ้งซ่อมไม่ได้ (ข้อความอธิบาย) เก็บ snapshot ห้อง/ชื่อ/เบอร์ไว้ในรายการ |
| สถานะ | `waiting` (รอการมอบหมาย) → `assigned` (มอบหมายแล้ว) → `inProgress` (กำลังซ่อม) → `done` (เสร็จสิ้น) ไปข้างหน้าอย่างเดียว ไม่ข้ามขั้น ไม่ย้อน; เก็บเป็นประวัติ ไม่คำนวณจากอย่างอื่น |
| มอบหมาย | นิติบุคคลมอบหมายได้เมื่อ `waiting` และเปลี่ยนช่างได้เมื่อ `assigned` (ช่างยังไม่เริ่ม); ตั้งแต่ `inProgress` เปลี่ยนไม่ได้ |
| ช่าง | `tech01` ได้เบอร์ของตนเอง (`DEMO_TECH_PHONE = '0800000002'`) เหมือนที่ทำกับ `tenant01`; รายชื่อช่างอยู่ในข้อมูลงานซ่อม (3 คน รวม `tech01`) จับคู่กับผู้ใช้ด้วยเบอร์โทร ช่างเห็น/อัปเดตได้เฉพาะงานที่มอบหมายให้เบอร์ตน |
| แจ้งเตือน | อยู่ในข้อมูลงานซ่อม (ผู้รับ = เบอร์โทร หรือ `role:juristic`): แจ้งซ่อมใหม่ → นิติบุคคล; มอบหมาย/เปลี่ยนช่าง → ช่างคนนั้น; เปลี่ยนสถานะโดยช่างหรือมอบหมายแล้ว → ผู้เช่า กดแล้วไปรายการนั้น (`?request=<id>`) |
| กระดิ่งรวม | hook `useNotifications()` รวมแจ้งเตือนบิลกับงานซ่อมเป็นรูปแบบเดียว (id, ที่มา, ข้อความ, วันที่, อ่านแล้ว, ปลายทาง, ฟังก์ชันทำเครื่องหมายอ่าน) กระดิ่งแสดงให้ทุกบทบาท |
| รหัสรายการ | `MR-0001`, `MR-0002` … = ค่ามากสุดที่มีอยู่ + 1 (ไม่ซ้ำแม้มีสองแท็บ เพราะอ่านใหม่ก่อนเขียนทุกครั้ง) |
| ข้อมูลหาย/เสีย | seed ใหม่เหมือนบิล; ข้อมูลที่อ้างห้องซึ่งหายไปบางส่วนต้องไม่ถูกล้าง (เรียนรู้จากรอบบิล) ล้างเฉพาะเมื่ออ้างห้องที่ไม่มีอยู่เลยสักห้อง |

## 4. ข้อมูลและกฎ

- `MaintenanceRequest`: `id`, `code`, `unitId`, `unitCode`, `leaseId`, `tenantName`, `tenantPhone`, `category` (`electrical | plumbing | airConditioning | furniture | other`), `title`, `description`, `photos: {name, dataUrl}[]`, `createdAt`, `assigneeId?`, `status`, `history: {status, at, note, byName}[]` (รายการแรก = `waiting` ตอนสร้าง)
- `Technician`: `id`, `name`, `phone`
- `MaintenanceNotification`: `id`, `type` (`requestCreated | assigned | statusChanged`), `requestId`, `recipient`, `createdAt`, `read`, `status?`
- กฎล้วน (`rules.ts`): `validateRequest` (หมวดหมู่ถูกต้อง, หัวข้อ 1–80 ตัวอักษร, รายละเอียด 1–1000, รูป 1–3), `canAssign`, `nextStatus`, `canTechnicianUpdate`, `visibleTo`(role/เบอร์), `nextCode`
- ข้อผิดพลาดจาก api: `invalid_input` (พร้อมคีย์ข้อความรายช่อง), `not_found`, `invalid_transition`, `not_assigned`, `no_lease`, `storage_failed`
- `MaintenanceApi`: `load`, `createRequest(input)`, `assign(requestId, technicianId)`, `updateStatus(requestId, status, note)`, `markRead`, `markAllRead(recipient)`; การเขียนเป็นอ่านใหม่แล้วเขียนแบบซิงโครนัสหลัง `await property.load()` เหมือน billing

## 5. หน้าจอ

- **ผู้เช่า:** หัวข้อ + ปุ่มแจ้งซ่อมใหม่; การ์ดรายการ (รหัส, หัวข้อ, หมวดหมู่, ป้ายสถานะ, วันที่); กดเปิดรายละเอียด (รูปขนาดเล็ก กดดูใหญ่ได้, ช่างที่รับงาน, เส้นเวลา); ฟอร์มใน Modal: เลือกรูปหลายรูป มีตัวอย่างและปุ่มลบรูป, ตรวจก่อนส่ง, โฟกัสช่องแรกที่ผิด, กันกดซ้ำ; ไม่มีสัญญา → ข้อความแทนฟอร์ม; ไม่มีรายการ → ข้อความว่าง
- **นิติบุคคล:** การ์ดสรุปจำนวนตามสถานะ, ตาราง (รหัส, ห้อง, ผู้เช่า, หมวดหมู่, หัวข้อ, ช่าง, สถานะ, วันที่) กรองสถานะ, รายละเอียดมีรูป/เส้นเวลา และกล่องเลือกช่างเพื่อมอบหมาย (ยืนยันก่อน)
- **ช่าง:** การ์ดงานของตน เรียงงานยังไม่เสร็จก่อน; รายละเอียดพร้อมรูป; ปุ่มทำขั้นถัดไปเพียงปุ่มเดียว ("เริ่มซ่อม", "ซ่อมเสร็จ") พร้อมช่องหมายเหตุ
- **กระดิ่ง:** ใน header ทุกบทบาท (รวมกับของบิล) ใช้ได้เหมือนเดิม: ตัวเลข `99+`, อ่านทั้งหมด, กดแล้วทำเครื่องหมายอ่านและไปที่รายการ
- ข้อความทั้งหมดผ่าน i18n (th/en); ตารางอยู่ในกล่องเลื่อนข้าง; รูปภาพมี `alt`; ป้ายสถานะมีข้อความเสมอ; ไม่ล้นจอที่ 320px; Modal ใช้งานได้ที่จอเตี้ย

## 6. การทดสอบ

กฎล้วนทุกกรณีขอบ (สถานะ, สิทธิ์เห็น/แก้, รหัสถัดไป); api: สร้าง/มอบหมาย/อัปเดต, ลำดับสถานะผิด, ช่างผิดคน, ไม่มีสัญญา, พื้นที่เก็บเต็มแล้วไม่สร้างรายการ, สองแท็บสร้างพร้อมกันได้รหัสไม่ซ้ำ, ข้อมูลเสีย/อ้างห้องบางส่วนหาย; UI: ฟอร์มไม่แนบรูปเรียก api ไม่ได้ + ข้อความ + โฟกัส, ไฟล์ผิดชนิด/ใหญ่เกิน/เกิน 3 รูป, กดซ้ำเรียกครั้งเดียว, ผู้เช่าเห็นเฉพาะของตน, ช่างเห็นเฉพาะงานตน, `?request=` ของคนอื่นไม่เปิด, แจ้งเตือนถึงผู้รับที่ถูกต้องเท่านั้น, กระดิ่งรวมนับถูก; ตรวจบนเบราว์เซอร์จริงที่ 1280/390/320px และจอเตี้ย 480px พร้อมย่อรูปจริง

## 7. ความเสี่ยง

- localStorage ประมาณ 5 MB ทั้งแอป: รูป 3 รูปต่อรายการประมาณ 30–60 KB ต่อรายการ เพียงพอสำหรับการสาธิต แต่ไม่ใช่ที่เก็บจริง ผู้ใช้เห็นข้อความเมื่อเต็ม
- รูปไม่ผ่านการตรวจเนื้อหา/ไวรัส (ตัวจำลอง) และไม่ตรง NFR1/NFR8 เชิงความปลอดภัย
- การย่อรูปพึ่ง canvas ของเบราว์เซอร์ (HEIC จากโทรศัพท์บางรุ่นอาจย่อไม่ได้ → แสดงข้อความไฟล์ไม่รองรับ)
- สิทธิ์เป็นฝั่งไคลเอนต์เท่านั้น (ตัวจำลอง) หลังบ้านจริงต้องตรวจซ้ำ
