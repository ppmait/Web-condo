# Common-Area Booking & Parcels — Design Spec

วันที่: 2026-11-09
Requirement: PDF ITDS262 — FR22 (ผู้เช่าจองส่วนกลาง), FR23 (ผู้เช่าดูสถานะส่วนกลาง), FR24 (นิติบุคคลลงทะเบียนพัสดุรับเข้า), FR25 (แจ้งเตือนพัสดุที่มาส่งไปยังผู้เช่า); use case "จองส่วนกลาง": กรอกไม่ครบกดยืนยันไม่ได้และแจ้งว่ากรอกไม่ครบ, สถานะเริ่มต้น "รอยืนยันการจองส่วนกลาง", แจ้งเตือนไปยังนิติบุคคล
แบบอ้างอิงหน้าตา: `facility_booking`, `my_parcels_smart_locker_hub`, `facility_booking_parcel_hub` ใน zip Stitch (เฉพาะส่วนที่ตรง FR)
ต่อจาก: `2026-11-09-maintenance-design.md` (รูปแบบเดียวกัน: กฎล้วน → api จำลองใน localStorage → Provider → หน้าจอ)

## 1. เป้าหมาย

ผู้เช่าดูส่วนกลาง จอง และติดตามการจอง นิติบุคคลยืนยัน/ปฏิเสธการจองและลงทะเบียนพัสดุที่มาส่ง ผู้เช่าเห็นพัสดุของตนและได้รับแจ้งเตือน ทั้งหมดเป็นข้อมูลจำลองในเบราว์เซอร์ (ไม่มีหลังบ้าน) และสลับเป็นหลังบ้านจริงได้โดยเขียน `FacilitiesApi` ตัวใหม่

## 2. ขอบเขต

- **ผู้เช่า** `/tenant/facilities`: การ์ดส่วนกลาง 4 แห่ง (ชื่อ, เวลาเปิด-ปิด, เปิดให้จอง/ปิดปรับปรุง, ที่ว่างของแต่ละช่วงในวันที่เลือก), ฟอร์มจอง (ส่วนกลาง, วัน, ช่วงเวลา, จำนวนผู้ใช้), โควตาที่เหลือของสัปดาห์, ประวัติการจองของตนพร้อมสถานะ และปุ่มยกเลิก (FR22, FR23) `/tenant/parcels`: พัสดุรอรับและรับแล้วของห้องตน (FR25)
- **นิติบุคคล** `/juristic/parcels-bookings` สองแท็บ: *การจอง* — การ์ดนับตามสถานะ, ตารางคำขอ กรองสถานะ, ยืนยัน/ปฏิเสธ (ปฏิเสธต้องมีเหตุผล), ปิด-เปิดส่วนกลางชั่วคราว; *พัสดุ* (`/parcels`) — ลงทะเบียนพัสดุรับเข้า (FR24), ตารางพัสดุ กรองสถานะ, ทำเครื่องหมายรับแล้ว
- **กระดิ่งรวม** เพิ่มแหล่งที่สามจากโมดูลนี้ (hook `useNotifications` เดิม)

**ไม่ทำรอบนี้:** QR Code เข้าประตู/ตู้ล็อกเกอร์อัจฉริยะ, มอบสิทธิ์รับพัสดุแทน, หน้าตั้งค่ากฎ/โควตา/ส่วนกลาง, นิติบุคคลจองแทนลูกบ้าน, ค่าบริการ/มัดจำ, พิมพ์รายงาน, แจ้งเตือนพัสดุค้างซ้ำ, แก้ไข/ลบพัสดุหลังลงทะเบียน, push จริง (NFR5)

## 3. การตัดสินใจ

| เรื่อง | ตัดสินใจ |
|---|---|
| ส่วนกลาง | 4 แห่งเป็นข้อมูลตั้งต้น ไม่มีหน้าจัดการ: `pool` ความจุ 20, `fitness` 15, `meeting` 10, `bbq` 12 คนต่อช่วง; เปิด 06–22 (pool/fitness), 08–20 (meeting), 10–21 (bbq) ชื่อแสดงผ่าน i18n ตาม `key` |
| ช่วงเวลา | รายชั่วโมงเต็ม `startHour`–`endHour` (ไม่รวมชั่วโมงปลาย) จองครั้งละ 1–3 ชั่วโมงต่อเนื่องภายในเวลาเปิด |
| จำนวนผู้ใช้ | `people` 1–5 (ผู้จอง + ผู้ติดตามไม่เกิน 4 ตาม mockup) |
| ล่วงหน้า | วันที่จองอยู่ระหว่าง พรุ่งนี้ ถึง วันนี้ + 14 วัน (ไม่จองวันนี้ เพราะระบบไม่รู้เวลาปัจจุบันของผู้ใช้อย่างน่าเชื่อถือ) |
| ความจุ | ทุกชั่วโมงในช่วงที่ขอ ผลรวม `people` ของการจอง `pending`+`confirmed` ของส่วนกลางและวันเดียวกัน + คนที่ขอ ต้อง ≤ ความจุ; เกิน → `no_capacity` |
| โควตา | ห้องละไม่เกิน 2 การจองที่ `pending`+`confirmed` ในสัปดาห์เดียวกัน (สัปดาห์ = จันทร์–อาทิตย์ ตามวันที่ใช้บริการ ไม่ใช่วันที่กดจอง); ที่ 3 → `quota_exceeded`; ยกเลิก/ปฏิเสธคืนโควตา |
| ปิดปรับปรุง | `closed` ห้ามจองใหม่ (`closed`); การปิดไม่ยกเลิกการจองเดิมโดยอัตโนมัติ (นิติบุคคลปฏิเสธเอง) |
| ห้องของผู้เช่า | จากเบอร์โทรบัญชี → สัญญาที่ใช้งานอยู่วันนี้ (เหมือนงานซ่อม); ไม่มี → `no_lease`; เก็บ snapshot ห้อง/ผู้เช่า |
| สถานะการจอง | เก็บ ไม่คำนวณ: `pending` (รอยืนยันการจองส่วนกลาง) → `confirmed` หรือ `rejected` (ต้องมีเหตุผล ≤ 300 ตัวอักษร); ผู้เช่ายกเลิกคำขอตนได้เมื่อ `pending`/`confirmed` และวันที่ใช้บริการยังไม่ถึง (→ `cancelled`); ตัดสินได้เฉพาะ `pending` ที่วันที่ใช้บริการยังไม่ผ่าน; สถานะปลายทางเปลี่ยนต่อไม่ได้; ทุกการเปลี่ยนต่อท้ายประวัติ `{status, at, note, byName}` |
| ตรวจซ้ำตอนยืนยัน | ยืนยันตรวจว่ายังเป็น `pending` เท่านั้น (ความจุถูกนับไว้แล้วตอนจอง) สองแท็บกดพร้อมกันได้ผลเดียว |
| พัสดุ | `Parcel`: `carrier` 1–40 (บังคับ), `trackingNo` ≤ 40 (ไม่บังคับ), `location` (`frontDesk` \| `locker`), ห้องเลือกจากห้องที่มีสัญญาที่ใช้งานอยู่วันนี้; ผู้รับ = ผู้เช่าของสัญญานั้น (snapshot); สถานะ `waiting` → `pickedUp` (หมายเหตุไม่บังคับ ≤ 300); ไม่มีแก้ไข/ลบ; รหัส `PK-0001` |
| แจ้งเตือน | จองใหม่ → `role:juristic`; ยืนยัน/ปฏิเสธ → ผู้เช่า; ผู้เช่ายกเลิก → `role:juristic`; พัสดุมาถึง → ผู้เช่า (เบอร์ตามสัญญา); ปลายทางเมื่อกด: `/tenant/facilities?booking=<id>`, `/tenant/parcels?parcel=<id>`, `/juristic/parcels-bookings?booking=<id>` หรือ `/juristic/parcels-bookings/parcels?parcel=<id>`; `?booking=`/`?parcel=` ที่ไม่ใช่ของผู้ใช้/ไม่มี → เพิกเฉยและล้างพารามิเตอร์ |
| รหัส | `BK-0001`… และ `PK-0001`… = ค่ามากสุดที่มี + 1 |
| ข้อมูลหาย/เสีย | คีย์ `condo:facilities` = `{ version: 1, facilities, bookings, parcels, notifications }`; seed ใหม่เมื่อว่าง/เสีย; อ้างห้องหายบางส่วนต้องไม่ล้าง (ล้างเฉพาะเมื่อไม่มีห้องที่อ้างเหลือเลย); การเขียนที่คนพึ่งพา (จอง ตัดสิน ยกเลิก ลงทะเบียนพัสดุ ปิด-เปิดส่วนกลาง) เขียนแบบเคร่งครัด: เขียนไม่ได้ → `storage_failed` และไม่เปลี่ยนอะไร; `markRead` ใช้หน่วยความจำสำรอง |

## 4. ข้อมูลและกฎ

- `Facility`: `id`, `key`, `openHour`, `closeHour`, `capacity`, `closed`, `closedNote?` (อยู่ในข้อมูลที่เก็บ เพื่อให้ปิด-เปิดได้)
- `Booking`: `id`, `code`, `facilityId`, `unitId`, `unitCode`, `leaseId`, `tenantName`, `tenantPhone`, `date`, `startHour`, `endHour`, `people`, `status`, `createdAt`, `history[]`
- `Parcel`: `id`, `code`, `unitId`, `unitCode`, `leaseId`, `tenantName`, `tenantPhone`, `carrier`, `trackingNo?`, `location`, `status`, `registeredAt`, `history[]`
- กฎล้วน (`rules.ts`): `validateBooking(input, facility, today)` (ส่วนกลางมีอยู่, วันที่จริงและอยู่ในช่วงล่วงหน้า, ชั่วโมงเป็นจำนวนเต็ม, 1–3 ชั่วโมง, อยู่ในเวลาเปิด, `people` 1–5), `hourlyLoad(bookings, facilityId, date)`, `availableAt(...)`, `weekOf(date)`, `quotaUsed(bookings, unitId, date)`, `canCancel`, `canDecide`, `validateParcel`, `nextCode`
- ข้อผิดพลาด: `invalid_input` (พร้อมคีย์รายช่อง), `not_found`, `invalid_transition`, `no_lease`, `no_capacity`, `quota_exceeded`, `closed`, `not_owner`, `storage_failed`
- `FacilitiesApi`: `load`, `createBooking`, `cancelBooking(id, actorPhone)`, `decideBooking(id, decision, reason, actorName)`, `setFacilityClosed(id, closed, note)`, `registerParcel(input, actorName)`, `markPickedUp(id, note, actorName)`, `markRead`, `markAllRead(recipient)`; การเขียนทำบนสำเนาและเขียนแบบเคร่งครัด อ่านใหม่ก่อนเขียนทุกครั้งโดยไม่มี `await` คั่น

## 5. หน้าจอ

- **ผู้เช่า/ส่วนกลาง:** การ์ด 4 ใบ ตัวเลือกวัน (พรุ่งนี้–14 วัน) แสดงที่ว่างรายชั่วโมงเป็นแถบพร้อมตัวเลข; ฟอร์มใน Modal: ส่วนกลาง, วัน, เวลาเริ่ม, ระยะเวลา (1–3 ชม.), จำนวนผู้ใช้; ตรวจก่อนส่ง โฟกัสช่องแรกที่ผิด กันกดซ้ำ ข้อความเฉพาะสำหรับ `no_capacity`/`quota_exceeded`/`closed`/`no_lease`/`storage_failed`; ประวัติการจองพร้อมเส้นเวลา/เหตุผลที่ปฏิเสธ; ยกเลิกผ่านกล่องยืนยัน
- **ผู้เช่า/พัสดุ:** การ์ดพัสดุรอรับ (ขนส่ง, วางที่ไหน, วันที่มาถึง) และประวัติที่รับแล้ว; ข้อความว่าง
- **นิติบุคคล/การจอง:** การ์ดนับ 4 สถานะ, ตาราง + กรอง, รายละเอียด, ยืนยัน (กล่องยืนยัน) / ปฏิเสธ (กล่องมีช่องเหตุผลบังคับ), ปุ่มปิด-เปิดส่วนกลางต่อแห่ง
- **นิติบุคคล/พัสดุ:** ปุ่ม "ลงทะเบียนพัสดุ" (ห้อง, ขนส่ง, เลขติดตาม, ที่วาง), ตาราง + กรอง, ปุ่มรับแล้ว (กล่องหมายเหตุ)
- **กระดิ่ง:** ข้อความใหม่ผ่าน i18n ปลายทางตามบทบาท; Modal ซ้อนต้องใช้ได้ด้วยคีย์บอร์ด (ใช้ Modal แบบสแตกที่แก้ไว้แล้ว)
- ข้อความทั้งหมดผ่าน i18n (th/en); ตารางในกล่องเลื่อนข้างที่เป็น `relative`; ป้ายสถานะมีข้อความเสมอ; ไม่ล้นจอที่ 320px; รหัส/ห้องไม่ตัดบรรทัดที่ขีด (`whitespace-nowrap`); key ของกล่องที่ซ้อนกันต้องไม่ซ้ำกัน

## 6. การทดสอบ

กฎล้วนทุกกรณีขอบ (ช่วงล่วงหน้า วันที่ 1/14/15, สัปดาห์ข้ามเดือน/ปี, ความจุพอดีและเกิน 1, โควตาที่ 2 และ 3, ช่วงทับซ้อนบางชั่วโมง); api: จอง/ยืนยัน/ปฏิเสธ/ยกเลิก, ทุกข้อผิดพลาด, จองพร้อมกันสองแท็บไม่เกินความจุและไม่เกินโควตา, ตัดสินซ้ำสองแท็บได้ผลเดียวและแจ้งเตือนครั้งเดียว, ปิดส่วนกลางแล้วจองไม่ได้, พื้นที่เก็บเต็มทุกการเขียนที่คนพึ่งพาแล้วไม่เปลี่ยนอะไร, ข้อมูลเสีย/อ้างห้องบางส่วนหาย, ผู้เช่าไม่มีสัญญา, ลงทะเบียนพัสดุให้ห้องที่ไม่มีสัญญา; UI: ผู้เช่าเห็นเฉพาะของตน, `?booking=`/`?parcel=` ของคนอื่นไม่เปิด, ฟอร์มไม่ครบเรียก api ไม่ได้ + โฟกัส, กดซ้ำเรียกครั้งเดียว, Modal ซ้อนใช้คีย์บอร์ดได้, กระดิ่งรวมสามที่มานับถูกและแจ้งถึงผู้รับที่ถูกต้องเท่านั้น; ตรวจบนเบราว์เซอร์จริงที่ 1280/390/320px และจอเตี้ย 480px

## 7. ความเสี่ยง

- ความจุและโควตาเป็นการตรวจฝั่งไคลเอนต์กับข้อมูลในเบราว์เซอร์เดียว หลายเครื่องจริงต้องให้หลังบ้านตัดสิน (ผู้ใช้หลายคนจองพร้อมกัน)
- "วันนี้" มาจากนาฬิกาเครื่องผู้ใช้ จึงจองได้เริ่มพรุ่งนี้เท่านั้น
- ตู้ล็อกเกอร์ไม่ได้เชื่อมระบบจริง `location` เป็นแค่ป้ายบอกที่วาง
- เบอร์โทรเป็นตัวตนเดียวที่เชื่อมบัญชีกับสัญญา (รับสืบมาจากบิลและงานซ่อม) สิทธิ์ตรวจฝั่งไคลเอนต์เท่านั้น
