# Mock Auth & Role Guard — Design Spec

วันที่: 2026-11-08
ต่อยอดจาก: `2026-11-08-frontend-foundation-design.md`
Requirement: PDF ITDS262 — FR1 (ผู้เช่าสร้างบัญชี), FR2 (ผู้เช่า/นิติบุคคล/ช่างเข้าสู่ระบบ)

## 1. เป้าหมาย

ให้ผู้ใช้สมัคร เข้าสู่ระบบ และเห็นเฉพาะหน้าของ role ตัวเอง โดย **ไม่มีหลังบ้าน** ข้อมูลทั้งหมดจำลองในเบราว์เซอร์ และแทนที่ตัวสลับ role ชั่วคราวใน header

เกณฑ์ความสำเร็จ:
- เปิดเว็บแล้วยังไม่ล็อกอินจะถูกพาไป `/login`
- ล็อกอินด้วยบัญชีทดลองของแต่ละ role แล้วเข้าหน้าแรกของ role นั้น และเห็นเมนูของ role ตัวเองเท่านั้น
- ผู้เช่าสมัครบัญชีใหม่แล้วล็อกอินได้ รีเฟรชแล้วยังล็อกอินอยู่
- เปลี่ยน URL ไป role อื่นไม่ได้ ถูกพากลับหน้าแรกของ role ตัวเอง
- `npm test` และ `npm run build` ผ่าน

## 2. ขอบเขต

**ทำ:** หน้า login, หน้าสมัคร (ผู้เช่าเท่านั้น), ออกจากระบบ, route guard ตาม role, เมนูผู้ใช้ใน header, ชั้นข้อมูลจำลองหลัง interface, i18n th/en ของทุกข้อความ

**ไม่ทำรอบนี้:** แก้ไขบัญชี (อยู่ในแผนภาพ ไม่อยู่ใน FR), ลืมรหัสผ่าน/OTP, หลังบ้านจริง, การเข้ารหัสระดับ PDPA (NFR1 เป็นหน้าที่ของหลังบ้าน), เนื้อหาโมดูลอื่น

## 3. การตัดสินใจ

| หัวข้อ | ตัดสินใจ |
|---|---|
| การสมัคร | เฉพาะ role ผู้เช่า (ตาม FR1) บัญชีนิติบุคคลและช่างมีแต่บัญชีทดลองที่ seed ไว้ |
| ฟิลด์สมัคร | username, password, ชื่อ-นามสกุล, email, เบอร์โทร (ตาม DFD "สร้างบัญชี") |
| เก็บข้อมูล | localStorage: `condo:users` (บัญชี), `condo:session` (id ผู้ใช้ปัจจุบัน) |
| รหัสผ่าน | เก็บเป็น hash SHA-256 (Web Crypto) ไม่เก็บ plain text; เซสชันเก็บแค่ id ผู้ใช้ |
| ชั้นข้อมูล | interface `AuthApi` แบบ async + `localAuthApi` เป็นตัวจำลอง; หน้าจอเรียกผ่าน `AuthProvider`/`useAuth()` เท่านั้น เมื่อมีหลังบ้านเปลี่ยนแค่ตัวสร้าง `AuthApi` |
| บัญชีทดลอง | seed 3 บัญชี (ผู้เช่า, นิติบุคคล, ช่าง) แสดงเป็นแผง "บัญชีทดลอง" บนหน้า login กดแล้วกรอกให้ ลบออกเมื่อมีหลังบ้านจริง |
| ผู้ใช้ที่ไม่มีสิทธิ์ | พาไปหน้าแรกของ role ตัวเอง (ไม่แสดงหน้า 403) |

## 4. ข้อมูลและกฎ

```ts
type Role = 'tenant' | 'juristic' | 'technician'   // มีอยู่แล้วใน src/app/roles.ts
interface User { id: string; username: string; fullName: string; email: string; phone: string; role: Role }
interface AuthApi {
  register(input: RegisterInput): Promise<User>       // role = 'tenant' เสมอ
  login(username: string, password: string): Promise<User>
  logout(): Promise<void>
  currentUser(): Promise<User | null>
}
```

กฎตรวจข้อมูลสมัคร (แสดงข้อผิดพลาดใต้ช่อง ผ่าน `FormField`):
- username 4–20 ตัว (a-z, 0-9, `_`) ไม่ซ้ำ (ไม่สนตัวพิมพ์เล็ก/ใหญ่)
- password อย่างน้อย 8 ตัว และต้องกรอกยืนยันให้ตรงกัน
- ชื่อ-นามสกุลไม่ว่าง; email รูปแบบถูกต้อง; เบอร์โทร 10 หลักขึ้นต้น 0
- login ผิดแสดงข้อความเดียว "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง" (ไม่บอกว่าผิดช่องไหน)

## 5. หน้าจอและ route

- `/login`, `/register`: หน้าเดี่ยว (ไม่ใช้ AppShell) ตรงกลางจอ มี `LanguageToggle` รองรับมือถือ
- `/` → ไป home ของ role ถ้าล็อกอินอยู่ ไม่งั้นไป `/login`
- `/tenant/*`, `/juristic/*`, `/technician/*` ต้องล็อกอิน และ role ต้องตรงกับ prefix
- ล็อกอินอยู่แล้วเข้า `/login` หรือ `/register` → ไป home ของ role
- header: เอา `RoleSwitcher` ออก ใส่เมนูผู้ใช้ (ชื่อ, ป้าย role, ปุ่มออกจากระบบ) ออกจากระบบแล้วไป `/login`
- ระหว่างโหลดเซสชันแรกแสดงสถานะกำลังโหลด ไม่วาบหน้า login

## 6. การจัดการข้อมูลเสียหาย

- `condo:users` ว่าง/เสียหาย/รูปแบบผิด → ถือว่าไม่มีผู้ใช้ แล้ว seed บัญชีทดลองใหม่ ไม่ทำให้แอปพัง
- `condo:session` ชี้ไปผู้ใช้ที่ไม่มีอยู่ → ล้างเซสชันแล้วถือว่ายังไม่ล็อกอิน
- localStorage เขียนไม่ได้ → สมัคร/ล็อกอินยังทำงานในหน่วยความจำของแท็บนั้น (ไม่คงอยู่หลังรีเฟรช) ไม่ throw

## 7. การทดสอบ

- `localAuthApi`: สมัครสำเร็จ/username ซ้ำ (ต่างตัวพิมพ์)/ฟิลด์ผิด, login สำเร็จ/ผิด, logout, เซสชันคงอยู่ข้ามการสร้าง api ใหม่, seed เมื่อข้อมูลเสียหาย, session ชี้ผู้ใช้ที่ไม่มี, storage throw
- หน้า login/register: ตรวจฟอร์ม, ข้อผิดพลาดใต้ช่อง, ล็อกอินแล้วไป home ของ role, แผงบัญชีทดลองกรอกให้
- Guard: ไม่ล็อกอินเข้า `/tenant/billing` ไป `/login`, tenant เข้า `/juristic/*` ถูกพากลับ `/tenant/overview`, ล็อกอินแล้วเข้า `/login` ถูกพากลับ
- Header: เห็นชื่อ/role, ออกจากระบบแล้วกลับ `/login`, ไม่มี RoleSwitcher
- ข้อความ th/en ครบทุกคีย์ใหม่

## 8. ความเสี่ยง

- ตัวจำลองไม่ปลอดภัยจริง (localStorage แก้ได้เอง) ใช้เพื่อพัฒนาหน้าจอเท่านั้น ห้ามถือว่าตรง NFR1
- หลายแท็บเปิดพร้อมกันอาจเห็นเซสชันไม่ตรงกัน ยอมรับในรอบนี้
- Web Crypto ต้องใช้งานได้ใน jsdom ถ้าไม่ได้ จะต้องให้ `localAuthApi` รับตัว hash เป็น dependency แล้วฉีดตัวทดสอบเข้าไป
