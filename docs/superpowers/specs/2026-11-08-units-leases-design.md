# Units, Leases & Inspections — Design Spec

วันที่: 2026-11-08
ต่อยอดจาก: `2026-11-08-mock-auth-design.md`
Requirement: PDF ITDS262 — FR3–5 (เพิ่ม/แก้ไข/ลบห้องชุด), FR6–8 (สร้าง/แก้ไข/ยกเลิกสัญญาเช่า), FR9–10 (บันทึกตรวจสภาพห้องก่อนย้ายเข้า/ย้ายออก)
แบบอ้างอิงหน้าตา: `unit_lease_management` ใน zip Stitch (ทำเฉพาะส่วนที่ตรง FR ตามขอบเขต A)

## 1. เป้าหมาย

ให้เจ้าหน้าที่นิติบุคคลจัดการห้องชุด สัญญาเช่า และบันทึกตรวจสภาพห้องได้ครบวงจร ในหน้า `/juristic/units` โดยไม่มีหลังบ้าน (ข้อมูลจำลองใน localStorage)

เกณฑ์ความสำเร็จ:
- เพิ่ม แก้ไข ลบห้อง; สร้าง แก้ไข ยกเลิกสัญญา; บันทึกตรวจเข้า/ตรวจออก ทำได้ครบและข้อมูลอยู่หลังรีเฟรช
- สถานะห้องและสัญญาที่แสดงสอดคล้องกันเสมอ (ไม่มีห้อง "ว่าง" ที่มีสัญญาใช้งานอยู่)
- เปิดครั้งแรกเห็นข้อมูลตัวอย่าง (ห้อง/สัญญา/บันทึกตรวจ) ไม่ใช่หน้าว่าง
- เฉพาะ role นิติบุคคลเข้าได้ `npm test` และ `npm run build` ผ่าน

## 2. ขอบเขต

**ทำ:** 3 แท็บ (ห้องชุด / สัญญาเช่า / ตรวจสภาพ) พร้อมค้นหา-กรอง ฟอร์มใน Modal แผนยืนยันก่อนลบ/ยกเลิก การ์ดสรุป 4 ใบ ข้อความ th/en ครบ

**ไม่ทำรอบนี้:** ผังชั้นอาคาร, ประวัติโอนกรรมสิทธิ์, หุ้นเจ้าของร่วม, escrow มัดจำ, พิมพ์/ส่งออกสัญญา, รูปถ่ายประกอบการตรวจ (ต้องมีที่เก็บไฟล์ของหลังบ้าน), หน้าของผู้เช่า/ช่าง, เชื่อมกับมิเตอร์และบิล (โมดูลถัดไป)

## 3. การตัดสินใจ

| หัวข้อ | ตัดสินใจ |
|---|---|
| ผู้ใช้ | role `juristic` เท่านั้น (guard เดิมของ `/juristic/*` พอ) |
| ที่เก็บข้อมูล | localStorage คีย์เดียว `condo:property` = `{ version: 1, units, leases, inspections }` ข้อมูลผิดรูป/เสีย/ว่าง → seed ตัวอย่างใหม่ทั้งก้อน (กัน reference ค้าง) |
| ชั้นข้อมูล | interface `PropertyApi` แบบ async + `localPropertyApi`; หน้าจอเรียกผ่าน `PropertyProvider`/`useProperty()` เท่านั้น เปลี่ยนเป็นหลังบ้านจริงโดยเปลี่ยนตัวสร้าง api |
| กฎธุรกิจ | ฟังก์ชันล้วนใน `src/property/rules.ts` (ไม่แตะ React/storage) |
| ข้อมูลตัวอย่าง | ห้อง 24 (Tower A, B), สัญญา 9 (ใช้งาน/ใกล้หมด/หมดอายุ/ยกเลิก/ยังไม่เริ่ม), บันทึกตรวจ 6 ชื่อและเบอร์เป็นข้อมูลสมมติ ไม่ใช่บุคคลจริง |
| เงิน | บาทจำนวนเต็ม แสดง `฿1,234` ชิดขวา `tabular-nums` |
| วันที่ | เก็บ `YYYY-MM-DD`; แสดงปี พ.ศ. เมื่อภาษาไทย (`th-TH-u-ca-buddhist`, UTC) และ ค.ศ. เมื่ออังกฤษ; "วันนี้" มาจากฟังก์ชันเดียวที่เทสแทนค่าได้ |

## 4. โครงข้อมูลและกฎ

**Unit:** `id, code, tower, floor, areaSqm, type, ownerName, ownership, listRent, closed`
- `code` รูปแบบ `A-1204` (`^[A-Z]-\d{3,4}$`) ไม่ซ้ำ; `tower` = ตัวอักษรหน้า code; `floor` 1–99; `areaSqm` > 0 และ ≤ 999; `type` ∈ studio | oneBed | twoBed | threeBed; `ownership` ∈ ownerOccupied | forRent; `listRent` ≥ 0
- **สถานะที่แสดง (คำนวณ ไม่เก็บ):** `closed` → ปิดปรับปรุง; มีสัญญาใช้งานอยู่ → มีผู้เช่า; `ownerOccupied` → เจ้าของอยู่เอง; อื่นๆ → ว่าง
- ลบห้องไม่ได้ถ้ามีสัญญาใดๆ (ทุกสถานะ) ให้ใช้ "ปิดปรับปรุง" แทน; แก้ `code`/`ownership` ของห้องที่มีสัญญาไม่ได้

**Lease:** `id, unitId, tenantName, tenantPhone, startDate, endDate, monthlyRent, deposit, cancelledAt?, cancelReason?`
- สถานะที่แสดง (คำนวณ): ยกเลิก (`cancelledAt`) > หมดอายุ (`endDate` < วันนี้) > ยังไม่เริ่ม (`startDate` > วันนี้) > ใช้งาน; ใช้งานที่เหลือ ≤ 60 วันได้ป้าย "ใกล้หมดอายุ"
- ตรวจ: `startDate` < `endDate`; `monthlyRent` > 0; `deposit` ≥ 0; ชื่อไม่ว่าง; เบอร์ 10 หลักขึ้นต้น 0; ห้องต้องมีอยู่ ไม่ปิดปรับปรุง และ `ownership = forRent`; **ช่วงวันที่ห้ามซ้อนกับสัญญาที่ไม่ถูกยกเลิกของห้องเดียวกัน** (วันสิ้นสุดของสัญญาหนึ่งกับวันเริ่มของอีกสัญญาห้ามเป็นวันเดียวกัน)
- แก้ไขได้เฉพาะสัญญาที่ยังไม่ยกเลิกและยังไม่หมดอายุ; ยกเลิกได้ครั้งเดียว บันทึกวันที่และเหตุผล (ไม่บังคับ)

**Inspection:** `id, leaseId, type (moveIn | moveOut), date, inspector, items[], waterMeter?, electricMeter?, note`
- `items` คือรายการตรวจคงที่ 8 หมวด: ห้องนั่งเล่น, ห้องนอน, ห้องน้ำ, ครัว, ระเบียง, เครื่องปรับอากาศ, เครื่องใช้ไฟฟ้า, กุญแจ/คีย์การ์ด แต่ละหมวดมี `condition` ∈ ok | damaged | missing และหมายเหตุ (บังคับเมื่อไม่ใช่ ok)
- ต่อสัญญามีตรวจเข้าได้ 1 ครั้ง และตรวจออกได้ 1 ครั้ง; วันตรวจเข้า ≥ `startDate`; วันตรวจออก ≥ วันตรวจเข้า (ถ้ามี) ตรวจออกกับสัญญาที่ยกเลิกแล้วได้; แก้ไขบันทึกได้ ลบไม่ได้
- ผู้ตรวจตั้งต้นเป็นชื่อผู้ใช้ที่ล็อกอิน แก้ได้; เลขมิเตอร์เป็นจำนวนไม่ติดลบ (ไม่บังคับ)

ข้อผิดพลาดของชั้นข้อมูลเป็น `PropertyError` พร้อม code (`invalid_input`, `code_taken`, `unit_has_leases`, `unit_not_rentable`, `lease_overlap`, `lease_locked`, `inspection_exists`, `not_found`) ฟอร์มแปลงเป็นข้อความใต้ช่อง

## 5. หน้าจอ

- เส้นทาง: `/juristic/units` (ห้องชุด), `/juristic/units/leases`, `/juristic/units/inspections` เมนูข้างยัง active ทั้งสามหน้า แท็บเป็นลิงก์ที่มี `aria-current`
- **การ์ดสรุป (ทุกแท็บ):** ห้องทั้งหมด, ห้องว่าง, สัญญาใกล้หมดอายุ (≤ 60 วัน), สัญญาที่ยังรอตรวจเข้า
- **ห้องชุด:** ค้นหา (รหัสห้อง/ชื่อเจ้าของ), กรองอาคารและสถานะ, ตาราง (รหัส, อาคาร/ชั้น, ประเภท/ขนาด, เจ้าของ, สถานะ, ค่าเช่า, ปุ่มแก้ไข/ลบ), แบ่งหน้า 10 แถว, ปุ่ม "เพิ่มห้องชุด"
- **สัญญาเช่า:** กรองสถานะ, ตาราง (ห้อง, ผู้เช่า, ช่วงสัญญา, ค่าเช่า, สถานะ, แก้ไข/ยกเลิก/บันทึกตรวจ), ปุ่ม "สร้างสัญญาเช่า"
- **ตรวจสภาพ:** กรองประเภท, ตาราง (ห้อง, ผู้เช่า, ประเภท, วันที่, ผู้ตรวจ, จำนวนจุดที่ไม่ปกติ), ปุ่ม "บันทึกการตรวจ" (เลือกสัญญาและประเภทที่ยังไม่เคยตรวจ), คลิกแถวดูรายละเอียด/แก้ไข
- ฟอร์มทั้งหมดอยู่ใน `Modal` ใช้ `FormField` กดส่งซ้ำระหว่างรอไม่ได้ ผิดแล้วโฟกัสช่องแรกที่ผิด; ลบ/ยกเลิกต้องยืนยัน
- ตารางว่างแสดง "ไม่มีข้อมูล" ป้ายสถานะมีข้อความเสมอ (ไม่พึ่งสีอย่างเดียว) ข้อความไทยยาวต้องไม่ล้นบนจอ 390px

## 6. การทดสอบ

- `rules.ts` (ตัวใหญ่ที่สุด): สถานะที่แสดงทุกกรณี, ขอบ 60 วัน, ช่วงสัญญาซ้อน/ชิดกัน, ตรวจห้อง/สัญญา/ตรวจสภาพทุกฟิลด์, ลบห้องที่มีสัญญา, ตรวจเข้า/ออกซ้ำ
- `localPropertyApi`: CRUD, เหตุผลของแต่ละ `PropertyError`, ข้อมูลอยู่ข้ามอินสแตนซ์, ข้อมูลเสียหาย/ผิดรูปหลายแบบแล้ว seed ใหม่, storage อ่าน/เขียนไม่ได้ยังทำงาน, ล้มเหลวชั่วคราวไม่ถูกแคช
- หน้าจอ (React Testing Library): แต่ละแท็บแสดงข้อมูลตัวอย่าง, ค้นหา/กรอง/แบ่งหน้า, เพิ่ม-แก้-ลบห้องพร้อมข้อผิดพลาดใต้ช่อง, สร้าง-แก้-ยกเลิกสัญญา, บันทึกตรวจเข้า/ออก, ลบห้องที่มีสัญญาถูกปฏิเสธ, ตารางว่าง, สลับภาษา, ผู้เช่าเข้า URL นี้ถูกพากลับ
- ตรวจจริงในเบราว์เซอร์ที่ 1280/900/390px

## 7. ความเสี่ยง

- ขอบเขตพองเกินจากภาพร่าง Stitch: รอบนี้ล็อกตามข้อ 2 ส่วนที่เหลือเป็นรอบถัดไป
- กฎ "สถานะคำนวณจากวันที่" ทำให้ผลเปลี่ยนตามวัน เทสต้องแทนค่า "วันนี้" ไม่ใช่นาฬิกาจริง
- ข้อมูลตัวอย่างต้องผูกกับ "วันนี้" แบบสัมพัทธ์ (เช่นสัญญาที่ใกล้หมดใน 40 วัน) ไม่ฝังวันที่ตายตัว ไม่งั้นหน้าตัวอย่างจะเพี้ยนเมื่อเวลาผ่านไป
- ผูก `condo:property` ก้อนเดียว: ข้อมูลใหญ่ขึ้นจะเขียนทั้งก้อนทุกครั้ง ยอมรับได้สำหรับตัวจำลอง
